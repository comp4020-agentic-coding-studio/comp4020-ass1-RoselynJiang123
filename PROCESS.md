# Process — *Hearing Is a Map, Not a Volume Knob*

## What I built

A static interactive explainer showing that the cochlea represents frequency as place rather than treating hearing as one volume control. A visitor follows sound into the cochlea, then uses one persistent map to locate a frequency, remove a continuous region and compare what that gap attenuates. The visuals, generated audio and spectrum all express one causal chain: frequency → cochlear place → local damage → missing frequency detail. It is a simplified teaching model, not a hearing test or a simulation of one person's hearing.

## 1. Writing the contract before drawing the cochlea

The first decision happened before any feature code. A reversed cochlear map could still look convincing, so I did not start by asking for a polished visual. I expanded the bare `CLAUDE.md` into a project contract: one explanatory claim, one coordinate system, Greenwood mathematics, cautious medical wording and explicit exclusions, then asked for pure `placeToFrequency()`/`frequencyToPlace()` functions with numeric-anchor tests; one documented anchor was corrected when the implementation and test exposed a mismatch. I knew the foundation was reliable because the functions, docs and tests agreed before Stage 1 consumed them, so later visuals never needed a second mapping convention. Evidence: [5a50f6e...ac5a017](https://github.com/comp4020-agentic-coding-studio/comp4020-ass1-RoselynJiang123/compare/5a50f6e...ac5a017).

## 2. Making three stages prove one claim

The obvious implementation was three separate demonstrations. Instead, I built outward from the tested mapping and kept the explanation mechanically connected. Stage 1 placed the slider, travelling-wave peak and hair-cell response on the same unfolded map; Stage 2 added a pure gap model routed through the existing tone's filters; Stage 3 reused that interval for both a 24-band spectrum and a momentary original/gap audio comparison, with synthesis, melody, filtering and spectrum logic kept as separate testable modules. The black-box spec checked the visible causal sequence while unit tests checked the transformations underneath; I knew the idea held together because changing one gap drove both the visual attenuation and the A/B audio path. Evidence: [370a5e7...4c92ec9](https://github.com/comp4020-agentic-coding-studio/comp4020-ass1-RoselynJiang123/compare/370a5e7...4c92ec9). This came at a cost, though: the three stages worked, but the interface itself was hard to read, which made later changes difficult.

## 3. Orienting a novice without blocking the interaction

Once the core worked, the opening still assumed visitors already recognised the cochlea. A long anatomy explanation would have delayed the interaction, so I changed the harness first: `CLAUDE.md` gained explicit `orientation → cochlea-focus → find` states, a Skip route and accessibility requirements. I then implemented the state machine before the visuals, followed by an accessible ear hotspot, two original schematic SVGs and the unfold connection to the persistent map, making the introduction optional rather than a mandatory lesson. Transition tests proved that resize, animation completion and unrelated events could not advance state, and existing Stage 1–3 tests still passed through the new entrance. Evidence: [828a491...c3883d4](https://github.com/comp4020-agentic-coding-studio/comp4020-ass1-RoselynJiang123/compare/828a491...c3883d4).

## 4. Replacing exposed features with a guided explanation

The final correction was about comprehension, not capability. Showing every stage at once made the page read like a technical form, and "Play example" did not explain why voice and melody followed each other. I introduced progressive disclosure, then unified map input across explore, gap and compare modes so a Stage 2 drag could not also change frequency. `frequencyContext()` added familiar-sound anchors and a Greenwood-derived percentage from the base, and the comparison became a two-part voice/melody timeline with real gap-range status and a measured fallback clock for test environments without Web Audio. Tests covered mode isolation, frequency-label boundaries and timeline progress, so the correction stayed testable even without a real audio engine.
